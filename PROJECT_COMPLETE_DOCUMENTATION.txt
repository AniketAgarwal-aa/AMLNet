SECTION B: EXECUTIVE & TECHNICAL SUMMARIES (DOMAIN & SYNTHETIC DATA LIMITS)
================================================================================
1. Executive Summary:
   AMLNet is an advanced, domain-aware financial intelligence and graph machine
   learning research platform designed for anti-money laundering (AML) detection,
   transaction pattern analysis, and suspicious activity investigation.
   The system models financial ecosystems as directed multigraphs where nodes represent
   accounts and directed edges represent fund transfers. It fuses topological graph
   features, deep representation learning (Graph Neural Networks: GraphSAGE, GAT, GCN),
   gradient-boosted decision trees (HistGradientBoosting, Random Forest), rule-based
   heuristic typologies, and explainable AI (XAI) attribution engines into an
   investigation-grade analytical workstation.

2. Problem Solved:
   Traditional rule-based AML monitoring generates severe false-positive rates (often >95%),
   overwhelming compliance analysts while failing to detect sophisticated, distributed
   laundering topologies such as high-velocity cyclic flow, rapid fan-in/fan-out structuring,
   and synthetic identity dispersion. AMLNet demonstrates that combining topological GNN
   embeddings with calibrated tree ensembles achieves exceptional detection recall (up to
   99.7%–100% on candidate filtering) while maintaining transparent, human-auditable
   explanation rationales.

3. Synthetic Data Limits & Regulatory Disclaimer:
   [CRITICAL DOMAIN NOTICE]
   AMLNet is an academic and investigative research prototype evaluated exclusively on
   synthetically generated transaction data (deterministic AMLNet synthetic generators and
   IBM AMLSim agent-based simulations).
   - AMLNet outputs (risk scores, predicted probabilities, typology signals) do NOT
     constitute a legal determination of criminal conduct, regulatory suspicion, or
     formal Suspicious Activity Report (SAR) filing requirement.
   - The platform does not ingest or process Personally Identifiable Information (PII)
     or real banking records.
   - Model recall and precision figures reflect synthetic data distributions and do not
     guarantee identical performance on production bank ledgers subject to real-world
     concept drift, evasion strategies, and unobserved counterparty dynamics.

SECTION G: DATABASE ARCHITECTURE: POSTGRESQL (NEON) & SQLITE (RESEARCH INVESTIGATION)
================================================================================
AMLNet employs a dual-scope database architecture strictly separating live operational
demonstration data from historical research investigation cohorts:

1. Operational Scope (Neon Serverless PostgreSQL):
   - Engine: PostgreSQL 16 on Neon Serverless.
   - Purpose: Real-time user interactions, investigation case tracking, dynamic
     alert triage, and demo transaction creation.
   - Seed State: Idempotently seeded on startup with 100 accounts (80 normal, 20 planted
     suspicious typologies) and 500 transactions.
   - Alembic Migration Head: `0001_initial`
   - Key Tables:
     * `accounts`: `id` (VARCHAR PK), `account_number`, `customer_name`, `balance`,
       `risk_score`, `risk_tier`, `created_at`.
     * `transactions`: `id` (VARCHAR PK), `source_account_id`, `target_account_id`,
       `amount`, `timestamp`, `transaction_type`, `is_sar`.
     * `alerts`: `id` (VARCHAR PK), `account_id`, `pattern_type`, `severity`, `status`.
     * `webauthn_credentials`: `id`, `user_id`, `credential_id`, `public_key`, `sign_count`.

2. Research Investigation Scope (SQLite: `backend/research/research_investigation.db`):
   - Engine: SQLite 3 (`WAL` journal mode, synchronous `NORMAL`).
   - Size: 15,151,104 bytes (14.45 MB).
   - Git Status: Explicitly tracked in Git repository (guaranteeing Render production
     availability without requiring multi-gigabyte raw AMLSim CSV mounts).
   - Content: Exact 25,000 account cohort sampled from IBM AMLSim 100K Tier:
     * 25,000 Accounts with precomputed topological graph metrics.
     * 35,000 Directed transaction edges.
     * 4,272 Confirmed SAR ground-truth labels.
   - Schema:
     * `investigation_accounts`: `account_id` (TEXT PK), `in_degree`, `out_degree`,
       `total_in_amount`, `total_out_amount`, `trans_count`, `sar_label`, `risk_score`.
     * `investigation_transactions`: `trans_id` (TEXT PK), `src`, `dst`, `amount`,
       `step`, `is_sar`.
     * `investigation_metadata`: `key` (TEXT PK), `val` (TEXT).

SECTION I: MACHINE LEARNING ENGINE: 6 ARCHITECTURES X 5 TIERS & BENCHMARK AUDIT
================================================================================
1. Evaluated Architectures:
   - Deep Graph Neural Networks (PyTorch Geometric):
     1. GraphSAGE: Inductive neighborhood aggregation via mean/max pooling.
     2. GAT (Graph Attention Network): Multi-head self-attention weighting neighbor edges.
     3. GCN (Graph Convolutional Network): Spectral first-order localized approximations.
   - Tabular Baselines (Scikit-Learn):
     4. HistGradientBoostingClassifier: Tree ensemble natively handling dense graph features.
     5. RandomForestClassifier: Bagged decision forest (100 estimators).
     6. LogisticRegression: L2-regularized linear baseline with balanced class weights.

2. Solved Zero-Recall Issue (Focal Loss & Threshold Tuning):
   Early baseline models suffered from severe class collapse (0% recall) due to extreme
   class imbalance (SAR prevalence < 0.2%).
   AMLNet resolved this through two rigorous techniques:
   - Binary Focal Loss: Focuses gradient updates on hard-to-classify minority examples:
     `FL(p_t) = -alpha * (1 - p_t)^gamma * log(p_t)` with `gamma=2.0`, `alpha=0.25`.
   - Validation Threshold Calibration: Decision thresholds are tuned on the validation
     split to maximize F1-score rather than assuming a naive 0.5 cutoff.

3. Published 30-Model Benchmark Performance Matrix (100K Tier Audited):
   Architecture           Accuracy  Precision  Recall    F1-Score  PR-AUC   ROC-AUC
   --------------------------------------------------------------------------------
   GraphSAGE              0.8410    0.5120     0.9970    0.6760    0.6840   0.9450
   GAT                    0.8350    0.5010     0.9980    0.6670    0.6720   0.9410
   GCN                    0.8290    0.4890     0.9950    0.6560    0.6580   0.9380

   Logistic Regression    0.7830    0.3940     0.5340    0.4530    0.4300   0.7700

4. Key Empirical Findings:
   - High-Recall Regime: GNNs achieve virtually complete capture (99.5%–99.8% recall)
     of suspicious entities, making them the optimal stage-1 candidate filter.
   - Precision & F1 Regime: Gradient-boosted trees maximize precision (74.5%) and F1
     (0.763) on node-aggregated topological features, making them ideal stage-2 scorers.

SECTION K: SECURITY & COMPLIANCE ARCHITECTURE: WEBAUTHN FIDO2 & THREAT REGISTER
================================================================================
1. Biometric WebAuthn Passkey Implementation:
   - Standard: FIDO2 / W3C WebAuthn Level 2.
   - Python Cryptographic Verification: `py_webauthn` 2.0+
   - Privacy Invariant: Zero biometric templates (fingerprint/face geometry) ever leave
     the user device or reach the server. Only cryptographic signatures are verified.
   - RP ID Resolution: Dynamic Relying Party ID bound to `amlnet.vercel.app`,
     `amlnet-api.onrender.com`, or `localhost`.

2. Hardened Security Controls (v2.2.2 Audit):
   - Origin Whitelisting: `ALLOWED_WEBAUTHN_ORIGINS` enforces strict origin matching:
     `https://amlnet.vercel.app`, `https://amlnet-api.onrender.com`, `http://localhost:5173`.
   - Referer Header Immunity: The authentication middleware rejects requests attempting
     to spoof origins via HTTP `Referer` headers.
   - Challenge Replay Protection: Challenges are stored in a single-use in-memory cache
     with a 300-second TTL. Once consumed or expired, a challenge cannot be replayed.
   - Admin Enrollment Gating: Registering new administrative passkeys requires passing
     the `X-Admin-Key` header, preventing arbitrary rogue credential enrollment.

3. Threat Register & Mitigations:
   - Threat: API Retraining Abuse -> Mitigation: WebAuthn administrative assertion gating.
   - Threat: Cross-Origin Hijacking -> Mitigation: CORS whitelist and origin enforcement.
   - Threat: SQL Injection -> Mitigation: SQLAlchemy 2.0 parameterized queries.
   - Threat: Memory Exhaustion (DoS) -> Mitigation: Graph subgraph queries capped at 250 nodes.

SECTION P: SCIENTIFIC CAVEATS, LIMITATIONS & FUTURE ROADMAP
================================================================================
1. Scientific Caveats & Known Limitations:
   - Synthetic Feature Artifacts: Features were computed on synthetic topologies; real
     money-laundering involves obfuscation techniques (mules, smurfing across multiple
     institutions) that single-institution simulations only partially capture.
   - Class Imbalance Sensitivity: In production environments with < 0.01% SAR prevalence,
     decision thresholds must be continuously re-calibrated.
   - Static Snapshot Assumption: Dynamic graph temporal evolution is approximated via
     time-window features rather than continuous-time dynamic graph neural networks (e.g., TGN).

2. Future Roadmap (Post-Release):
   - Temporal Graph Networks (TGN) for continuous-time edge streaming.
   - Multi-party privacy-preserving federated graph learning.
   - Enterprise SAML/OIDC SSO integration alongside WebAuthn passkeys.
   - Distributed graph processing via Apache Spark / GraphX for multi-billion edge graphs.
